# LinkLake v1.1.0

## 中文

v1.1.0 补齐 PostgreSQL 共享状态、高可用流量计量、证书维护和管理入口，并更新安装与日常使用文档。

### 主要变化

- **共享存储与 HA**：管理员、会话、客户端、八类策略、Fleet、证书/ACME、审计、指标、告警及更新任务使用共享 PostgreSQL；业务读取失败不回退各实例 SQLite。共享端口、实例租约和 fencing 约束过期 Leader。
- **Fleet 与流量**：Bundle v2 在同一事务中协调归属、凭据引用、generation、策略交换与流量规则。七种转发协议接入持久计量、共享速率窗口、完整 u64 配额和 UUID 去重；各实例保留持久 spool，并在正常停机时排空账务。
- **证书与界面**：Web UI 和 Flutter Manager 可配置 HTTP-01 / Cloudflare DNS-01、查看就绪状态并按角色权限操作；共享签发、DNS 清理和恢复遵循任务租约与策略版本。修复 Manager 的中文显示与 ACME 操作细节。
- **维护与部署**：新增 PostgreSQL 初始化、SQLite 迁移、回滚资格检查和停机材料密钥轮换命令。Helm 使用共享数据库及各副本独立持久卷；安装和更新流程阻止将 PostgreSQL 当作单机 SQLite 维护。动态出口保护修正 IPv6 云元数据地址匹配。
- **使用文档**：新增[完整使用说明](https://github.com/ASL-Vanity/LinkLake/blob/v1.1.0/docs/user-guide.zh-CN.md)，重写中英文 README，覆盖首次连接、协议策略、系统服务、HA、备份及更新。

### 升级与运行边界

- **SQLite → PostgreSQL 是显式停机迁移**：停止源进程及所有目标副本，保留源备份，按[迁移指南](https://github.com/ASL-Vanity/LinkLake/blob/v1.1.0/docs/storage-migration.md)初始化、导入并检查回执。目标产生新写入后，切回旧 SQLite 不能视为无损回滚。
- **材料密钥必须单独备份**：所有 PostgreSQL 副本使用同一份独立的 32 字节原始密钥；替换部署 Secret 不会重加密已有材料。[轮换命令](https://github.com/ASL-Vanity/LinkLake/blob/v1.1.0/docs/certificate-key-maintenance.md)要求所有副本停止。
- **HA 仍需持久存储与入口配置**：每个副本保留自己的身份、流量 spool 和暂存目录。故障接管不迁移既有 TCP/QUIC 会话，客户端和应用可能需要重连；永久丢失实例磁盘时，尚未上传的账务不能保证零丢失。数据库可用性和公网入口路由由部署方负责。
- **数据库恢复与二进制回退分开处理**：PostgreSQL 使用数据库备份/PITR，以及匹配的材料密钥和实例状态；单机 SQLite 快照或镜像回退不能恢复整个集群。候选程序启动后可能已经修改数据库，Linux 安装包不会在启动失败后自动降级旧程序。操作前阅读[集群升级与恢复](https://github.com/ASL-Vanity/LinkLake/blob/v1.1.0/docs/postgres-upgrades.md)。

### 平台与资产验证

Windows x86_64、Linux x86_64 提供核心与 Manager 发行包；服务端容器目标为 `linux/amd64`，并提供 Compose/Helm 部署配置。macOS 保留源码和 CI 兼容性，暂无官方发行资产或自动更新通道。

**Windows 官方包按个人开源策略有意不使用 Authenticode 签名。** 安装前验证 SHA-256、GitHub 构建证明和生产 Ed25519 更新清单；Linux 另验证 OpenPGP 签名，OCI 镜像按摘要验证签名及构建来源。开发签名不能替代生产更新信任。详见[发布供应链说明](https://github.com/ASL-Vanity/LinkLake/blob/v1.1.0/docs/release-supply-chain.zh-CN.md)。

版本发布不表示既有生产节点已经升级；生产部署应根据各自状态与恢复方案安排。

## English

v1.1.0 completes shared PostgreSQL state, HA traffic accounting, certificate maintenance and management controls, with updated installation and daily-use documentation.

### Changes

- **Shared storage and HA:** PostgreSQL stores administrators, sessions, clients, all eight policy kinds, Fleet, certificate/ACME material, audit, metrics, alerts and update tasks. Shared-read failures never fall back to instance-local SQLite. Shared ports, instance leases and fencing constrain stale leaders.
- **Fleet and traffic:** Bundle v2 reconciles ownership, credential references, generations, policy swaps and traffic rules in one transaction. Seven forwarding protocols use durable metering, shared rate windows, full-range u64 quotas and UUID deduplication. Each instance persists a traffic spool and drains accounting during orderly shutdown.
- **Certificates and interfaces:** Web UI and Flutter Manager expose HTTP-01 / Cloudflare DNS-01 configuration, readiness and role-based controls. Shared issuance, DNS cleanup and recovery follow task leases and policy revisions. Manager Chinese labels and ACME interaction details are corrected.
- **Maintenance and deployment:** New commands initialize PostgreSQL, migrate SQLite, verify rollback eligibility and rotate material keys offline. Helm uses a shared database and independent persistent volumes. Installation/update safeguards prevent PostgreSQL from entering standalone SQLite maintenance flows. Dynamic egress protection corrects IPv6 cloud-metadata matching.
- **Documentation:** A new [complete user guide (Chinese)](https://github.com/ASL-Vanity/LinkLake/blob/v1.1.0/docs/user-guide.zh-CN.md) and rewritten bilingual READMEs cover enrollment, policies, system services, HA, backups and updates.

### Upgrade and operational boundaries

- **SQLite → PostgreSQL is an explicit offline migration.** Stop the source process and every target replica, retain the source backup, and follow the [migration guide](https://github.com/ASL-Vanity/LinkLake/blob/v1.1.0/docs/storage-migration.md) for initialization, import and receipt checks. Switching back to old SQLite after new target writes is not a lossless rollback.
- **Back up the material key separately.** Every PostgreSQL replica uses the same independent 32-byte raw key. Replacing a deployment Secret does not re-encrypt stored material. [Key rotation](https://github.com/ASL-Vanity/LinkLake/blob/v1.1.0/docs/certificate-key-maintenance.md) requires every replica to be stopped.
- **HA still needs persistent storage and ingress routing.** Each replica retains its own identity, traffic spool and staging directory. Takeover does not migrate existing TCP/QUIC sessions, so clients and applications may need to reconnect. Permanent loss of an instance disk can lose accounting that has not yet been uploaded. Database availability and public ingress remain deployment responsibilities.
- **Database recovery and binary rollback are separate operations.** Use PostgreSQL backup/PITR with matching material keys and instance state. A standalone SQLite snapshot or image rollback does not restore the cluster. Candidate startup can already change the database; Linux packages do not automatically downgrade after activation failure. Read [cluster upgrades and recovery](https://github.com/ASL-Vanity/LinkLake/blob/v1.1.0/docs/postgres-upgrades.md) before maintenance.

### Platforms and asset verification

Core and Manager release packages target Windows x86_64 and Linux x86_64. Server containers target `linux/amd64`, with Compose/Helm deployment configuration. macOS remains source- and CI-compatible, with no official release assets or automatic-update channel.

**Official Windows packages intentionally omit Authenticode signing under the personal open-source release policy.** Before installation, verify SHA-256, GitHub build attestations and the production Ed25519 update manifest. Also verify Linux OpenPGP signatures and OCI signatures/provenance against the image digest. Development signatures are not production update trust. See the [release supply-chain guide](https://github.com/ASL-Vanity/LinkLake/blob/v1.1.0/docs/release-supply-chain.md).

Publishing a version does not imply that existing production nodes have been upgraded. Schedule deployment around each environment's state and recovery plan.
